# Phase 5: Environment Upgrade & MicroPython Execution

**Date:** June 28, 2026
**Author:** Mayank (wolgwang)
**Project:** SeedSigner Secure Boot — Summer of Bitcoin

## 1. Overview
In Phase 5, the primary goal was to upgrade our build environment to support a wider array of ESP32 devices and ensure that I can correctly load and boot the official MicroPython build for the ESP32-S3 via our stateless Secure Loader.

## 2. Environment Upgrades
- **ESP-IDF Update**: Upgraded the environment to **ESP-IDF v6.0.1** to take advantage of recent hardware support and bug fixes, specifically ensuring `esp32p4` and related MCUs are properly supported by the toolchain.
- **QEMU Update**: Updated `qemu-system-xtensa` to `esp_develop_9.2.2_20250817` to overcome bugs in older QEMU releases (such as missing `esp32s3` features or incomplete emulation).

## 3. Loading MicroPython on ESP32-S3
I transitioned from loading the dummy `hello_world.bin` payload to booting the real SeedSigner MicroPython payload (`WAVESHARE_ESP32_S3_TOUCH_LCD_35B/micropython.bin`) generated by the `seedsigner-micropython-builder`.

### Challenges & Resolutions

1. **Bare-metal Flash Reading**:
   When reading from the SPI flash in the secure loader, the generic HAL function (`esp_flash_read`) failed because it relied on FreeRTOS features that are not initialized in our lightweight secure bootloader.
   - *Resolution*: Replaced `esp_flash_read` with the ROM function `esp_rom_spiflash_read()`, which successfully mapped the flash directly into RAM.

2. **Partition Overflows**:
   The MicroPython binary (~1.6MB) exceeded the generic 2MB `storage` partition limit in our `partitions.csv`, causing `NoFreeClusterException` when preparing the virtual SD card image.
   - *Resolution*: Increased the `storage` partition size from 2M to 4M.

3. **Cache Invalidation Hanging**:
   I experienced silent hangs during the jump to the payload due to aggressive cache invalidation occurring before the payload was fully copied.
   - *Resolution*: Moved cache invalidation steps to *after* all `memcpy()` operations were complete, just before the final execution branch.

4. **Payload Segment Extraction**:
   Initially, the secure loader attempted to boot a full flash image (which included the ROM bootloader), leading to missing IROM/DROM segments and `Guru Meditation Error` (IllegalInstruction).
   - *Resolution*: I correctly isolated the MicroPython application partition (which has 7 segments including mapped memory), and successfully signed and packaged that specific payload.

5. **MMU Mapping Bugs**:
   I encountered `[XTS-AES] Physical Adress greater than 0x00FFFFFF` errors from QEMU when the payload accessed DROM/IROM. This was caused by two issues:
   - **Page Truncation**: The `pages` calculation floored the required pages instead of rounding up, leaving the tail end of the segments unmapped.
   - **Invalid Bits**: I resolved a QEMU-specific XTS-AES bug by explicitly initializing the entire `ESP32S3_MMU_TABLE` with 0s (Valid, Physical Page 0) before applying our safe MMU mappings.

### Result
The Secure Bootloader now successfully sets up the Cache MMU logic, loads the IRAM/DRAM segments, maps the IROM/DROM segments, and executes the MicroPython `app_main` without any crashes on the ESP32-S3 emulator.

## 4. Investigating Future Devices (`esp32p4` and others)
*Note: Optimization and full hardware implementation for these platforms are planned for future work.*

### Compilation Fixes for ESP32-P4 (RISC-V)
To support the RISC-V architecture of the `esp32p4`:
1. **Compiler Flags**: Removed the hardcoded `-mlongcalls` flag from `specter_crypto/CMakeLists.txt`. This flag is specific to the Xtensa architecture and causes compilation failures on RISC-V compilers.
2. **Assembly Instructions**: Replaced inline Xtensa assembly (`movi`) used for stack pointer tracking with standard C code or RISC-V compatible instructions (`li sp`).
3. **Macro Redefinitions**: Addressed `-Werror` build failures caused by redefining macros like `SOC_IROM_LOW` and `SOC_IROM_HIGH` by wrapping them in `#ifndef` guards.
4. **Cache Invalidation API**: The legacy ROM functions (`Cache_Invalidate_ICache_All` and `Cache_Invalidate_DCache_All`) are not available on the ESP32-P4. The previous attempt to use `cache_ll_invalidate_all()` failed as the function did not exist in the HAL. I resolved this by explicitly using the `esp32p4` specific ROM function `Cache_Invalidate_All(0x33)` (passing `CACHE_MAP_MASK`).
5. **Alignment Warnings**: Fixed `-Waddress-of-packed-member` compilation errors by correctly aligning packed structs (`bl_section_t` and `custom_esp_image_header_t`) as local variables in memory.

During testing, I attempted to boot the secure loader on the `esp32p4` emulator (`esp-emu`). 
- **Limitations**: I discovered that QEMU's emulation for the `esp32p4` mask ROM currently has severe limitations. The ROM boot process consistently crashes with bus faults (unmapped memory accesses), resulting in unrecoverable exception loops.
- **Workarounds Tried**: 
  - I attempted to bypass the eFuse writing crash by completely disabling Secure Boot in `sdkconfig` and configuring `CONFIG_SECURE_BOOT_INSECURE`. However, the ROM still crashed in the same manner.
  - I attempted to bypass the mask ROM entirely using `--skip-rom` to boot directly into our Secure Loader. Our bootloader successfully began execution (printing `boot: ESP-IDF 2nd stage bootloader`), but quickly crashed with bus faults because bypassing the ROM leaves core hardware components uninitialized.
- **Conclusion**: I confirmed that this is an `esp-emu` emulator bug and not a codebase flaw. Because of this, further testing of the successfully compiling cryptographic logic for `esp32p4` currently requires physical hardware.
